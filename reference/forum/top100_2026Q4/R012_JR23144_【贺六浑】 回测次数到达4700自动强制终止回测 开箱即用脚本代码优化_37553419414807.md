### 核心原理

我们在跑回测的主程序之外，开一个 **后台监控线程** 。 这个线程每隔几秒钟就去问一下服务器：“我现在用了多少次了？” 一旦发现回测次数超过设定的阈值（比如 4700 次），它就会 **直接拔电源** （强制杀掉进程），强行留下 300 次给咱们早上起来“手动操作”或“AI 优化”的空间。

### 准备工作

### 开箱即用代码

代码分为两部分：

1. **高精度查询函数  和 监控函数** （自动处理夏令时，不需要手动改UTC偏移量）。
2. **主程序** （直接替换你原本的运行入口）。

#### 第一步：把这个查询函数加到你的代码里

这个版本上个硬减 13 小时的代码更稳，直接定位纽约时区。

```
from datetime import datetime, timedeltaimport pytzimport threadingimport timeimport osimport asyncio# 假设你已经导入了 wqb 相关库def get_today_simulations_count(session):    """    获取当前纽约时间当天的回测提交数量    自动处理夏令时(DST)，无需手动计算时差    """    try:        # 直接定位纽约时间        ny_tz = pytz.timezone('America/New_York')        today_start = datetime.now(ny_tz).replace(hour=0, minute=0, second=0, microsecond=0)        tomorrow_start = today_start + timedelta(days=1)        payload = {            'limit': 1,            'offset': 0,            'status': 'UNSUBMITTED\x1fIS_FAIL',             'dateCreated>': today_start.isoformat(),            'dateCreated<': tomorrow_start.isoformat(),            'hidden': 'false'        }        response = session.get(            'https://api.worldquantbrain.com/users/self/alphas',             params=payload,            timeout=10        )        response.raise_for_status()        return response.json().get('count', 0)    except Exception as e:        print(f"[查询API波动] 暂时无法获取数量: {e}")        return 0 # 返回0防止误杀，或者根据需求处理# ---------------- 配置区域 ----------------SAFE_LIMIT = 4700  # 你想保留的阈值CHECK_INTERVAL = 30  # 检查间隔(秒)，建议30秒，太快费API，太慢容易超def monitor_quota_and_kill():    # 在线程里单独登录一次，避免和主线程session冲突    s_monitor = login()    while True:        try:            # 查询当前用量            current_num = get_today_simulations_count(s_monitor)            print(f"[监控中] 当前回测次数: {current_num}")            if current_num > SAFE_LIMIT:                print(f"\n" + "!" * 40)                print(f"!!! 警告：回测次数达到 {current_num}，超过阈值 {SAFE_LIMIT} !!!")                print("!!! 正在强制终止进程以保护资源 !!!")                print("!" * 40 + "\n")                # os._exit(0) 是核弹级退出，不给主线程任何反应机会，直接杀                # 这样才能确保不会多跑任何一个测试                time.sleep(1)                os._exit(0)        except Exception as e:            # 监控线程报错不要停，继续下次检查            pass        time.sleep(CHECK_INTERVAL)
```

### 评论 #6 (作者: XL21212, 时间: 2个月前)

把每日额度分成两段——前 4700 次用于可中断的批量执行（后台运行），后 300 次只允许手动提交或选定的关键因子通过。这样不需要依赖暴力杀进程，而是从请求发起时就检查剩余额度，低于阈值就直接拒绝非紧急请求。优点是减少 API 波动带来的误杀（原帖的查询函数在出错时返回 0，可能触发过早终止），且避免杀掉进程后丢失中间状态。

**需要验证的地方是** ：原帖的监控线程独立登录，会不会因为 token 不一致或 session 过期导致计数不准，又或者由于网络延迟导致检测到超限时已有额外请求在途中，实际占用额度超过 4700。如果结合请求前预检和事后核对，会不会更可控？

### 评论 #7 (作者: XT66957, 时间: 2天前)

脚本思路很好，我用的是同一套。有三处边界建议再收一下：

**1）判定用  `>=`  而不是  `>` 。** 写成  `if current_num > SAFE_LIMIT`  时，正好落在 4700 那一次不会触发——此时额度已经用掉 4700，而不是你想要的“留 300”。改成  `>=`  才会在到达瞬间就停。

**2）查询函数出错时  `return 0`  是个隐患。** 你在注释里也提了“返回0防止误杀”，但方向反了：平台限流或网络抖动时返回 0，看门狗会认为“才用了 0 次”，于是 **该杀的时候不杀** ，一路跑爆。这是典型的静默失效——不报错、不告警，只是保护没生效。建议异常时返回  `None` ，主循环收到  `None`  就跳过本轮判断并计数，连续 N 次拿不到数就告警，而不是当成 0。

**3）监控线程单独  `login()`  会和主线程抢登录。** 平台认证是会话级的，两条线程各自认证会互相把对方的 session 顶掉，表现是主线程跑着跑着突然一片 401 / CANCELLED。我在并发场景踩过这个。建议监控线程复用主线程的 session，或者把查询封装成带重试的独立请求。

最后提一句  `os._exit(0)` ：它确实是最干净的“拔电源”，但它会跳过所有  `finally`  和  `atexit` ，正在写的日志和中间结果文件不会 flush，可能留下半截 JSON。如果你的主程序是断点续传的，建议杀之前先把进度落盘。

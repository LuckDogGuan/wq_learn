> 本篇是六维拯救计划之：OpCount

现在大家基本都用 AI 来挖因子了，AI 通常喜欢持续堆叠，哪里不对点哪里，有时候会导致因子复杂度急剧上升，通常表现在：

1. 过度堆叠字段，单因子 alpha0 拓展成组合因子：a0*alpha0 + a1*alpha1 + ...
2. 过度嵌套操作符，因子后面都没法看了 op(op(op(...)))
3. 防御性挖掘，AI通常喜欢加一些防御性的操作符，来保证计算的有效性，例如 abs() 保证为正，inverse(x + 0.01) 保证分母不为零，ts_backfill(winsorize(.)) 叠加保证因子有效等，但其实这些操作符是否有用，要看用到的数据字段本身的特点。

给大家分享一个可以在不改变因子表现的前提下，对因子进行化简的 skill，拯救六维中的 OpCount：

# Alpha Simplification Workflow

This skill is for semantic-preserving simplification, not idea replacement.

Use it after a signal already makes economic sense and preferably already has a working baseline.

For detailed simplification heuristics and tested examples, see [reference.md](reference.md).

All proposed rewrites must remain valid FastExpr.

When writing or simplifying expressions, follow the syntax habits in `BRAIN_Consultant_Starter_Handbook.md` and verify operator usage against `squadb/knowledge/BRAIN Platform Operators ALL.md`.

## Core Principle

Keep the signal idea unchanged:

- Same economic story

- Same primary fields

- Same ranking / exposure intent

- Similar or better submission profile

If a change alters directionality, timing, coverage logic, or risk budget in a meaningful way, treat it as an alpha redesign, not simplification.

Also remember that operator count is a real computational budget:

- all operators count, including arithmetic, comparison, and boolean operators

- repeating the same operator expression multiple times increases count multiple times

- simplification is not only about deleting wrappers, but also about rewriting the same logic with fewer operator evaluations

When operator syntax or arity is unclear, check `squadb/knowledge/BRAIN Platform Operators ALL.md`.

If a simplification is mathematically neat but awkward, unsupported, or ambiguous in FastExpr syntax, reject it.

## Step 1: Lock the Baseline

Fetch baseline stats before simplifying:

- `get_alpha`

- `get_submit_check`

- `calc_self_corr`

- `get_prod_corr`

- `get_yearly_stats` when stability matters

Record:

- original expression

- operator count estimate

- Sharpe / Fitness / Turnover

- current fails or warnings

## Step 2: Generate Simplification Candidates

Prefer 4-8 tightly scoped variants rather than one big rewrite.

Each candidate should remove only one logical class of complexity at a time unless a pair is obviously linked.

Write candidates in valid FastExpr form, not pseudo-code.

Good candidate classes:

- remove sign-invariant wrappers

- merge linear subexpressions

- remove redundant robustness operators

- remove cosmetic sub-signal weights

- remove denominator safety constants when truly unnecessary

- test removing `ts_backfill` even though it does not count toward operator count

- extract repeated subexpressions into temporary variables

- replace nested binary aggregation with one multi-input operator when supported

## Step 3: Classify Changes by Safety

Use two buckets:

### A. Verified-safe simplifications

These are simplifications whose semantics are structurally preserved and also confirmed by simulation.

Examples:

- removing `reverse(x)` inside `abs(...)`

- removing `reverse(x)` when the next meaningful operator is sign-invariant, such as `ts_std_dev`

- merging obviously linear pieces when platform behavior remains unchanged in tests

### B. Empirical simplifications

These are changes that often preserve intent but may change NaN handling, cross-sectional shape, or tail behavior.

Examples:

- removing `winsorize`

- removing `abs`

- removing sub-signal weights

- removing denominator protection constants

- removing `ts_backfill`

Treat these as candidate variants, not identities.

## Step 4: Simulate in Small Batches

Use `simulate` to test candidates under the original production settings unless the simplification itself requires a special diagnostic run.

Compare against baseline on:

- Sharpe

- Fitness

- Turnover

- concentration / sub-universe behavior

- self correlation

- prod correlation

Do not accept a lower-operator version automatically.

Prefer the simplest expression that still preserves stable PnL and economic sense.

## Step 5: Validate Submission Quality

For the top 1-2 candidates:

- run `get_submit_check`

- run `calc_self_corr`

- run `get_prod_corr`

- check `get_yearly_stats` if the baseline was yearly-sensitive

If two variants are close, prefer the one with:

- fewer warnings

- cleaner unit behavior

- simpler explanation

- more stable yearly profile

## Step 6: Report the Outcome Clearly

Summarize simplification in three layers:

1. safest accepted simplification

2. more aggressive simplification that still worked empirically

3. simplifications tested but rejected

Always state whether a candidate is:

- mathematically/structurally safe

- only empirically acceptable

- rejected because it changed behavior

## Best Practices

- Keep the simplification cycle short: usually 1-2 rounds.

- Remove one complexity source at a time before combining removals.

- Do not sacrifice stable PnL just to save one operator.

- If a robustness wrapper is removed, verify that weight concentration and sub-universe behavior did not quietly worsen.

- Use `newtmcp` for all platform interaction.

- When in doubt, preserve economic clarity over minimal operator count.

- If `op(field)` appears repeatedly, compute it once, assign it to a variable, and reuse the variable.

- Prefer operators with unlimited inputs such as `add(f1, f2, f3)` over chained binary forms when the logic is the same.

- Keep every rewrite compatible with FastExpr punctuation, operator signatures, and statement style from `BRAIN_Consultant_Starter_Handbook.md`.

## reference.md

# Simplifying BRAIN Alphas Without Changing Meaning

This reference collects high-value simplification patterns for FastExpr alphas.

Use it after reading [SKILL.md](SKILL.md).

## 0. Syntax Constraint

Every simplification must still be expressible in valid FastExpr.

Before accepting a rewrite, confirm:

- the expression follows FastExpr syntax conventions from `BRAIN_Consultant_Starter_Handbook.md`

- the operator exists in `squadb/knowledge/BRAIN Platform Operators ALL.md`

- the operator arity matches FastExpr support

- any temporary-variable rewrite still ends with a valid final output expression

Do not return pseudo-code, mathematical shorthand, or unsupported rewrite patterns as final recommendations.

## 1. How Operator Counting Really Works

In this project, count operators aggressively:

- arithmetic operators count

- comparison operators count

- boolean operators count

- each extra operator means one more computation

- repeating the same subexpression repeats the operator cost

This means simplification is often about expression layout, not just removing wrappers.

Two high-value rules:

### 1.1 Extract repeated subexpressions

If the same transform appears multiple times, compute it once and reuse it through a temporary variable.

Example:

```fastexpr

x = op(field);

add(x, multiply(x, y))

```

is often better than recomputing `op(field)` in multiple places.

Use this whenever:

- `rank(field)` appears more than once

- `ts_delta(field, d)` appears more than once

- a shared preprocessed signal feeds multiple branches

### 1.2 Prefer multi-input operators when available

For operators that accept unlimited inputs, use the one-call form.

Example:

- `add(f1, f2, f3)` counts once

- `f1 + f2 + f3` effectively creates multiple operations

The same idea often applies to other multi-input operators such as `multiply`, `max`, and `min` when supported.

Always verify exact operator support in `squadb/knowledge/BRAIN Platform Operators ALL.md`.

## 2. `abs` Can Sometimes Be Removed

Ask why `abs` is there:

- Is the input already non-negative by construction?

- Is the downstream operator sign-invariant?

- Was `abs` added only as a generic robustness wrapper?

Good removal cases:

- `abs(x)` where `x` is already non-negative

- `reverse(abs(x))` when only magnitude matters downstream

- `abs(...)` before a sign-invariant dispersion operator, if sign information is already irrelevant

Risk:

- Removing `abs` can change long/short direction or make tails asymmetric.

- Treat most `abs` removals as empirical unless non-negativity is obvious.

## 3. `winsorize` May Be Redundant

`winsorize` is often used defensively, but it is not always needed.

Good times to test removal:

- downstream is `rank`, `group_rank`, `quantile`, or another operator that already compresses tails

- truncation / neutralization / ranking already keeps exposure well-behaved

- baseline has no weight concentration problem

What to re-check after removal:

- concentration warning

- sub-universe Sharpe

- yearly drawdown shape

Do not assume it is safe just because the final operator is a rank.

## 4. Denominator Safety Constants

Examples include:

- `divide(x, y + 0.1)`

- `inverse(max(y, 0.1))`

- `divide(x, max(abs(y), 0.01))`

These often exist only to avoid zero denominators.

You may test removing or shrinking them when:

- the denominator field is structurally positive

- the denominator is never near zero in practice

- the constant is large enough to distort the true signal

High caution:

- This can materially change scale and tail behavior.

- Prefer test variants such as remove / shrink / replace with milder guard.

## 5. Sub-Signal Weights Can Be Cosmetic

Weighted sums are common:

- `add(multiply(a, 0.6), multiply(b, 0.4))`

- `a * 2 + b`

If the result is later ranked, group-ranked, normalized, or neutralized, exact weights may not matter much.

Good tests:

- drop all weights to equal-weight form

- remove only clearly cosmetic multipliers

- preserve signs first, then test removing magnitude differences

Risk:

- Weights sometimes encode real preference, timing, or turnover control.

- If a weight controls a hedge leg or volatility leg, do not remove it casually.

## 6. `ts_backfill` Does Not Count, But Still Deserves Testing

Even though `ts_backfill` does not increase operator count, it can still hurt signal quality.

Always consider two variants:

- keep `ts_backfill`

- remove `ts_backfill`

Why removal can help:

- stale values may pollute fast changes

- backfilled data may create fake persistence

- missingness itself may contain information

Why removal can hurt:

- coverage drops

- long/short counts collapse

- sub-universe performance weakens

This is usually an empirical choice, not a semantic identity.

## 7. Linear and Sign-Invariant Simplifications

These are the first places to look for safe reductions.

Examples:

- `reverse(abs(x)) -> abs(x)`

- `ts_std_dev(reverse(x), d) -> ts_std_dev(x, d)`

- `subtract(ts_delta(a, 1), ts_delta(b, 1)) -> ts_delta(subtract(a, b), 1)` only after simulation confirms behavior

- if `op(field)` is reused across branches, assign it once before combining branches

- if a sum or product is just an aggregation, prefer one multi-input call over chained binary calls

Important:

- Some transforms are mathematically equivalent but not platform-equivalent in practice because of NaN handling, units, or operator implementation details.

- Treat any algebraic merge as verified-safe only after a simulation check.

## 8. Recommended Testing Order

Use this order because it gives the best chance of saving operators without accidentally changing the alpha:

1. remove obvious `reverse`

2. remove `abs` only when sign is provably irrelevant

3. merge linear terms

4. test `winsorize` removal

5. test `ts_backfill` removal

6. test denominator guard removal or shrinkage

7. test weight removal

## 9. Practical Acceptance Rules

Accept a simplification when:

- economic meaning is unchanged

- Sharpe / Fitness stay similar or improve

- no new concentration or sub-universe failures appear

- self/prod corr do not become materially worse

Reject or downgrade a simplification when:

- metrics fall noticeably

- yearly profile becomes less stable

- it introduces new warnings

- the expression becomes harder to explain despite fewer operators

## 10. Example From This Project

Original optimized form:

`group_rank(multiply(ts_std_dev(winsorize(ts_backfill(reverse(abs(subtract(ts_delta(f, 1), ts_delta(f, 1)))), 66), std=4), 22), less(rank(abs(ts_delta(f, 1))), 0.97)), subindustry)`

Verified-safe simplification:

`group_rank(multiply(ts_std_dev(winsorize(ts_backfill(abs(subtract(ts_delta(f, 1), ts_delta(f,f1))), 66), std=4), 22), less(rank(abs(ts_delta(f, 1))), 0.97)), subindustry)`

What changed:

- removed `reverse(...)` because it sat inside `abs(...)`

More aggressive empirical simplification that also worked in this case:

`group_rank(multiply(ts_std_dev(winsorize(ts_backfill(abs(ts_delta(subtract(f, f), 1)), 66), std=4), 22), less(rank(abs(ts_delta(f, 1))), 0.97)), subindustry)`

What changed:

- merged two `ts_delta` branches into one delta of a spread

Important project lesson:

- the same algebraic merge applied to the original unsimplified baseline changed metrics materially

- so even mathematically neat reductions must be verified on-platform

原帖提出的化简方向很实用，特别是针对冗余防御性操作符的清理。我有一个比较具体的边界情况想确认：在 reference.md 里提到简化要保留原始字段的排名/暴露意图，但有些表达式里  `ts_backfill(winsorize(...))`  这类嵌套其实是在改变数据分布的时序处理顺序，单纯去除外层包装后即使字段不变，回看窗口内的极端值填充逻辑也可能和原始设计不一样。如果要验证这个替代是否真的“语义不变”，除了对比 submission profile 里的 IC 和换手率，是不是还需要专门检查一下极端值样本的覆盖变化，才能排除简化带来的信息泄露风险。

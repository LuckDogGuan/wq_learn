## 一、按北京时间查询过滤

平台采用美国时间，位于西五区时区，而北京时间处于东八区时区。北京时间减去 13 小时即为美国时间，例如北京时间 13:00 时，美国时间为零点。

在时间转换过程中较为不便，能否直接用北京时间查询过滤？答案是可以的。

通过浏览器 F12 可查看查询接口：

```
https://api.worldquantbrain.com/users/self/alphas?limit=20&offset=0&status=UNSUBMITTED%1FIS_FAIL&dateCreated%3E=2024-12-13T00:00:00-05:00&dateCreated%3C2024-12-15T00:00:00-05:00&order=name&hidden=false

```

使用 “url 解码” 工具解码后得到：

```
https://api.worldquantbrain.com/users/self/alphas?limit=20&offset=0&status=UNSUBMITTEDIS_FAIL&dateCreated>=2024-12-13T00:00:00-05:00&dateCreated<2024-12-15T00:00:00-05:00&order=name&hidden=false
```

其中时间过滤条件如下：

```
dateCreated>=2024-12-13T00:00:00-05:00
dateCreated<2024-12-15T00:00:00-05:00

```

“-05:00” 表示西五区时区，北京东八区时区用 “+08:00” 表示。由于 “+” 号是特殊符号，需进行 “url 编码”，用 “%2B” 替换 “+” 号。若使用北京时间过滤，最终的 url 为：

```
https://api.worldquantbrain.com/users/self/alphas?limit=20&offset=0&status=UNSUBMITTED%1FIS_FAIL&dateCreated%3E=2024-12-13T00:00:00%2B08:00&dateCreated%3C2024-12-15T00:00:00%2B08:00&order=name&hidden=false

```

## 二、查询时间精确到时分秒

平台界面的时间范围仅能从某天查询到另一天。若需查询某天 1 点到 5 点的数据，可利用接口时间范围可指定时分秒的特性。查询语句如下：

```
https://api.worldquantbrain.com/users/self/alphas?limit=20&offset=0&status=UNSUBMITTED%1FIS_FAIL&dateCreated%3E=2024-12-13T01:00:00%2B08:00&dateCreated%3C2024-12-13T05:00:00%2B08:00&order=name&hidden=false

```

## 三、查询 check submission 结果是 pass 的 Alpha

通常通过 machine_lib 里的 check_submission () 方法检查可提交的 Alpha，先打印结果后在界面提交。若要直接在界面找到已检查通过的 Alpha，可对 check_submission 方法改造，将检查结果设为 Alpha 的名字，使用 set_alpha_properties 方法，代码示例：

```
def check_submission(alpha_bag, gold_bag, start):
        # 其他代码……
        check_result = get_check_submission(s, alpha_id)
        set_alpha_properties(s,alpha_id, name = f'{check_result}-{alpha_id}')
        # 其他代码……
```

如此，可通过名称包含 pass、fail 或 error 搜索对应 Alpha。

## 四、查询名称包含 A 或 B 的 Alpha

若查询名称包含 error 或 pass 的 Alpha，有两种方法。第一种是分别查询两次，一次查包含 error 的，一次查包含 pass 的。第二种是利用 api 支持的 “或” 逻辑，用 “%1F” 连接两个关键字，如下：

```
name=pass%1Ferror

```

同理，查询 tag 包含 A 或 B 标签的 Alpha 也可使用此方法。

## 五、查询 10000 条以上 Alpha

查询 api 用 limit 控制每页大小，最大值为 100；用 offset 控制翻页数量，最大值为 10000。若查询数据超 10000 条，会报错 “Invalid offset. Please use filters to narrow down the result.”。

解决方法是按时间分段查询，将大时间范围切分为小时间范围，最后合并结果。代码示例如下：

```
def pull_all(init_start_date: datetime, init_end_date: datetime):
    s = login()
    # 设置时间间隔为 3 小时
    delta_time = datetime.timedelta(hours=3)
    query_start_date = init_start_date
    all_alphas = []
    # 当查询开始时间小于查询结束时间时循环查询
    while query_start_date < init_end_date:
        query_end_date = query_start_date + delta_time
        # 若计算出的查询结束时间大于设定的总查询结束时间，则将其设为总查询结束时间
        if query_end_date > init_end_date:
            query_end_date = init_end_date
        # 根据设置的开始时间和结束时间获取 Alpha 数据
        alphas = get_alphas(start_date=query_start_date.strftime(time_format),
                            end_date=query_end_date.strftime(time_format),
                            session=s
                            )
        all_alphas.extend(alphas)
        query_start_date = query_end_date

```

### 评论 #4 (作者: PZ64174, 时间: 2个月前)

关于check_submission返回空但网页显示可提交的问题，这通常是因为self_correlation阈值导致的。API的check_submission会同时检查多个条件包括self_correlation，而网页界面可能会单独展示self_correlation的状态，所以看起来不一致。另一个可能的原因是alpha的子宇宙fitness在两次检查之间发生了变化，特别是当market regime切换时fitness可能快速下降。建议你显式查询self_correlation的值并与平台阈值对比，同时关注sub_universe_fitness的实时状态，这样能更准确地定位问题所在。

先谢楼主，第五节"按时间分段查询"的思路今天救了我。但我实测发现平台已经改过一版限制，把结论贴出来给还在用旧代码的人：

报错体也变了， **不再是** 帖子里写的  `"Invalid offset. Please use filters to narrow down the result."` ，现在是：

```
["Cannot display more than the first 1,000 alphas. Apply filters to narrow results and see more."]
```

⚠️ 所以两件事同时坏掉： **①**  阈值从 10000 掉到 1000，无过滤时你最多只能看到 **最近 1100 条** ； **②**  如果你的脚本是靠匹配旧报错文案来触发分片逻辑的，现在匹配不上，会走到"未知错误 → break"分支。

### 2. 这个坑有多隐蔽

我的全量扫描脚本就是这么中招的。它的翻页终止条件写的是"按响应里的  `count`  翻页"，而 **无过滤查询返回的  `count`  恒等于 10000** （被 cap 住的占位值，不是真实总数）。于是脚本以为要拉 10000 条，拉到 offset=1100 撞 400，重试 6 次后 break—— **整个流程 exit code 0，日志不报错，落盘文件也正常生成，只是里面少了一大半数据** 。这种"假成功"最难发现：我连续几天用它筛可提交 alpha，直到发现最近做的几条明明达标却从来不出现在清单里，才回头查。修复后同一账号： **1150 条 → 3031 条** 。

### 3. 分片实现的两个改进

楼主给的是"按固定天数切"，我建议改成 **按 count 自适应二分** ，理由是产量分布极不均匀（我这边一天能差 10 倍）：固定切法会同时出现"某天超 1000 被截断"和"某天 0 条白跑一次请求"。

```
PAGE_CAP = 1000

def shards(stage, lo, hi):
    """把 [lo,hi) 递归二分到每片 count <= PAGE_CAP"""
    c = query(stage, lo, hi, limit=1)["count"]
    if c == 0:
        return []
    d0, d1 = parse(lo), parse(hi)
    span = d1 - d0
    if c <= PAGE_CAP or span <= timedelta(minutes=1):
        return [(lo, hi, c)]
    mid = (d0 + span / 2).isoformat()
    return shards(stage, lo, mid) + shards(stage, mid, hi)

```

两个细节：

- **递归下探到分钟级，不要停在天级。**  我第一版停在"1 天"，结果碰到单日 1304 条的批量跑批日，那天直接被截掉 204 条——而且 **不会报错** ，又是一次静默丢数据。下探到分钟后彻底消失。
- **片界用  `dateCreated>`  /  `dateCreated<` （注意 URL 编码是  `%3E=`  /  `%3C` ），时区必须显式带上** ，如  `2026-08-01T00:00:00-04:00` 。用 requests 的  `params=`  传字典会自动编码，不用手拼。相邻片用同一个边界值即可，左开右闭不会重不会漏；保险起见我还是按 id 做了一次去重。

### 4. 顺带一个可以省掉大半请求的点

分片只解决"能不能拉全"，拉全之后逐条  `/check`  才是真瓶颈（我 3000 条跑一轮要一个多小时）。我加了个按 alpha_id 的  `/check`  结果本地缓存（TTL 12h，因为 PROD_CORRELATION 会随在产组合逐日漂移，不能永久缓存），命中率稳定在 95% 以上，一轮从 1 小时压到 3 分钟。缓存 key 只用 alpha_id，因为 IS alpha 的表达式和 setting 是不可变的。

如果谁的脚本最近"跑得通但结果变少了"，八成就是撞上这个。建议直接搜一下自己代码里有没有硬编码  `10000`  或者匹配旧报错文案的地方。

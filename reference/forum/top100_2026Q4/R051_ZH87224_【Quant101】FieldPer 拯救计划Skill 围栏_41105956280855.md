## 帖子正文

> 本篇是六维拯救计划之：FieldPer

最近参考 cnhkmcp 里的 improve-alpha-performance skill 开发了一个因子优化的 skill，用GEM+一二三阶挖出有信号的因子后，就丢给skill优化，优化目标是满足 RA 提交标准，但是用 AI 来挖因子有个问题，AI喜欢无限堆叠信号，往往一个 2Field 4Op 的因子最后虽然优化成功了，但是优化出来 8Field, 40Op （没错，我挖出好几个40+Op的因子，闹麻了）

经过一番研究，发现解决方案也很简单，就是给 skill 加上如下限制 prompt：

## Iteration and Best Practices

- **Cycle Limit**: 3-5 per alpha; pivot if stuck (e.g., new datafield).

- **Tracking**: Maintain a log (e.g., MD file with iterations, metrics deltas).

- **Efficiency**: Use parallel tools; focus 70% on ideas, 30% on tweaks.

- **Success Criteria**: Passing checks + stable yearly stats.

- **Keep Simple and Focus**: Final alpha's fields should less then 4, operators count should less than 8.

主要是最后一条：Keep Simple and  Focus。

这句话放在 Skill 里或者 Reference 里都可以，效果立竿见影

### 评论 #1 (作者: FF65210, 时间: 7天前)

FieldPer拯救计划的Skill围栏设计很有工程思维！FieldPer这个指标确实是字段管理的关键，但很多人对它的理解还停留在表层。你用Skill围栏来约束字段的滥用，这个思路把字段管理从被动补救变成了主动防控。有个问题想请教：Skill围栏的具体判定规则是什么？是按字段的历史出货率？还是按字段的PC贡献度？围栏触发后的处理流程是什么，是直接禁用字段？还是降级到观察名单？另外围栏的粒度怎么定，是字段级还是数据集级？我担心字段级太细碎，数据集级又太粗。还有FieldPer拯救的实操案例，有没有成功把低效字段救回来的例子？拯救和放弃的判断标准是什么？这套方法论如果标准化了，对团队的字段管理规范很有价值，期待后续更新！

## FastExpr 深入分析

首先我们需要来分析下 FastExpr 的本质。

在 FastExpr 的算子中，除了基础的变换、四则运算和逻辑等操作符外，核心的因子信号发生器有两种：截面算子和时序算子。

其中截面算子是在同一个时间节点，在整个投资标的池上进行运算，考虑的是单支股票与整体市场时间的关系，典型的有 rank(*)

而时序算子计算的是单支股票在过去一段时间上的表现，其考虑的是单支股票自身在一段时间内的变动信息，典型的有 ts_rank(*)

所以截面算子只需要最新时间点的一组向量数据，就可以完成计算；而时序算子需要最新时间点往前推T天的矩阵数据，才可以完成计算。

## PythonAlpha 回测引擎探索

平台的 PythonAlpha 为了避免因子作弊（用到未来函数），采用的是类似事件驱动的回测引擎，每天都会将最新的数据，以及过去一段时间的切片数据（切片长度可通过 lookback 设置），作为一个矩阵喂给 @alpha 装饰的信号，而我们的信号函数需要返回的是一个向量，是股票池中每只股票的因子值。

探索过 PythonAlpha 的小伙伴应该都发现了，如果 lookback 设置很大，有很大概率因子是跑不出来的，但实际上在 FastExpr 中，只有时序算子才需要传入矩阵，而截面算子只需要最新的向量即可，所以我们可以采用编程中常见的以空间换时间的思路，利用 store 滚动保存需要进行时序计算的组件，这样甚至 lookback 只需要 = 0 都可跑通。

2. 时序算子以矩阵做入参，但是只用最后 lookback 条来计算，避免多余计算

### 评论 #3 (作者: FF45555, 时间: 2个月前)

楼主这个从 Fast 算子本质拆解到 store 滚动保存时序组件、让 lookback=0 跑通的思路太扎实了——我当初也是卡在"Python 为什么不能像 Fast 一样一行 ts_rank"才摸到这套机制的。补几个楼主没展开、但实战高频踩的坑：

**第一，store 不是无限缓存，事件字段别进 store。**  楼主用 store 滚动存时序组件很妙，但 earnings 这类季度事件字段用 store 存历史会错位。我实测 store 存  `ts_backfill(earnings, 60)`  再读，事件窗口比直接用  `data.earnings[-1]`  还脏——store 是按"天"滚动的，没对齐财报可得日。事件类字段单独  `ts_backfill`  处理，别进 store。

**第二，float32 精度在长时序累积会截断。**  楼主说 lookback=0 靠 store 滚动跑通，但 store 里存 250 天的 float32，极端值会被截断。我有个 alpha IND/TOP3000/D1 累积长时序 store，float32 把尾部极端值截掉，信号失真，sharpe 虚高 0.1。长时序 store 建议中间转 float64 算完再回 float32。

**第三，py 复刻 fast 差的 10% 常在中性化层级。**  Fast 的  `group_neutralize(industry)`  在 Python 里要用专门的 group 操作，新手只写  `signal -= np.mean(signal)`  只是 MARKET 中性，行业暴露没消。想控行业用 group_neutralize(industry)。

接楼主：store 是空间换时间的好工具，但事件字段和 float32 精度是两个隐形雷，踩过才记得住。

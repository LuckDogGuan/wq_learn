## 帖子正文

Python alpha的存在解决了一些Fast Expression时期比较难做甚至完全做不到的问题。就比如，如何在我们构建alpha的时候剔除/保留一些特定的国家/行业呢？要实现这个操作首先需要我们在labs中先读取到这些group字段的数字与真实名称的对应关系，然后后续在构建alpha的时候再通过特定的代码予以剔除。

直接将下面这段代码复制进labs，把Region/Universe/Delay/GROUP_FIELD_ID改成你想要查看的字段然后运行即可。 **表格中的三列依次是：字段具体名称/对应的数字编号/股票数量**

> *如果你要查看不同地区的字段，由于braincache的存在有时候重新运行会报错，这时候重新启动一下kernel即可解决。*
> *另外如果你懒得查，最后我贴上了ASI MINVOL1M delay1的Country/Sector/Industry/Subindustry，以及EUR TOP2500 delay1的Country字段的数字id-字符串对应关系，你可以直接查看。需要注意的是，不同Region的同一个Sector编号并不是一样的。每个地区都要单独查询一下。*

### 评论 #1 (作者: QW94165, 时间: 1个月前)

这套映射思路很实用，特别是把字符串字段和 alpha 运行时的数值 code 对齐这一步，过去确实没有特别顺手的办法。有几个细节想跟你确认一下：

1. 代码里  `probe_start_date`  取的是  `raw_latest_date - 14 天` ，这里是用 14 天来覆盖 universe 数据的发布延迟吗？如果是的话，不同 delay/region 下这个窗口是否需要相应调整？

1. `codes_are_integer_like`  的判断用  `np.isclose(..., atol=1e-6)` ，对于本身就是 float 编码的 group 字段（比如某些分层字段）会被归到  `Float64`  分支，这种情况下后续在 alpha 里做  `group_code == NaN`  过滤会不会和 integer 字段行为不一致？有没有踩过坑？

1. 文末提到 braincache 导致切换 region 后报错需要重启 kernel，这个是  `BrainCache(probe_brain)`  缓存了上一个 region 的元数据导致的，还是  `raw_brain.get_data_frame`  那一步就拿到了脏数据？方便的话可以贴一下报错栈，方便后来人对照排查。

另外想请教一下，这套方法对  `event関連する` （related）这类返回多值/列表型字段也适用吗，还是只对单值分类字段成立？

### 评论 #3 (作者: XW23690, 时间: 1个月前)

这个工具太实用了！尤其是"不同Region的同一个Sector编号并不一样"这个提醒——我之前就踩过这个坑，用 USA 的 Sector ID 直接套到 EUR 上，结果回测出来的国家分布完全对不上。

补充一个批量查询的技巧：如果需要同时查多个 Region 的字段映射，可以改一下代码逻辑，把 REGION = "EUR" 改成一个列表循环，比如 for region in ["EUR", "USA", "ASI", "GLB"]:, 然后把结果存到一个统一的 DataFrame 里。这样可以一次性生成所有 Region 的对应表，避免重复运行。

另外，关于 BrainCache 报错的问题——除了重启 kernel，还有一个更简单的方法：在每次运行前加一行 BrainCache.clear(), 这样可以强制刷新缓存，不需要重启。不过注意这会增加运行时间，因为需要重新加载数据。

### 评论 #4 (作者: SY54221, 时间: 1个月前)

承接楼主关于查 group 字段字符串与数字 id 对应关系的思路，补充一个在 alpha 中实际使用这些 code 做剔除时的细节：

- 楼主提到不同 Region 的同名 Sector 编号不同，实操中若把查到的 code 硬编码进 Python alpha 做国家/行业剔除，换 region 时极易因编号错配导致过滤逻辑失效。
- 建议将映射表按 region 参数动态加载，而不是写死常量，这样在样本外切到新 universe 时仍能保持剔除逻辑可控，减少无谓的噪声。

# PPA Alpha 前后筛选流程

## 1. 三类规则的职责

### PPA 范围文件

`PPA 范围/*.json` 表示某一个 Power Pool 主题的适用边界，例如：

```json
{
  "theme_name": "GLB/D1 Power Pool Aug`26",
  "duration": {"start_date": "2026-07-27", "end_date": "2026-08-09"},
  "core_requirements": {
    "region": "GLB",
    "delay": 1,
    "universe": "TOPDIV3000",
    "neutralization": ["Slow Factors", "Fast Factors", "Slow + Fast Factors", "Crowding Factors", "RAM"],
    "forbidden_datasets": ["PV1", "MODEL110"]
  }
}
```

它负责 Region、Delay、Universe、主题允许的 Neutralization、禁用 Dataset 和主题有效期。
网页展示名和平台 API 枚举不能直接混比，例如 `RAM` 对应平台枚举
`REVERSION_AND_MOMENTUM`。

### 通用 PPA 标准

`不同阿尔法标准/ppa_alpha_standard.json` 负责通用门槛：Sharpe、Turnover、operator 数量、
非 support field 数量、Power Pool correlation 上限和 Description/奖项提示。

它不负责覆盖主题的 Region、Universe 或主题中性化列表。

### 平台实时事实

平台 Alpha 详情提供实际 settings、expression、dataset、fields 和指标；`check` 提供实时
检查结果。平台事实与主题要求不一致时是 `EXCLUDED` 或 `CONFLICT`，不能反向修改规则。

## 2. 前筛选：减少需要检查的 Alpha

1. 选择当前有效主题；多个主题同时有效时必须 `--scope` 指定。
2. 唯一窗口是最近 1 个月；可以使用 `--start-date` 和 `--end-date` 明确覆盖起止日期。两个月兼容模式已删除。
3. 查询 `type=REGULAR`、`status=UNSUBMITTED`、`instrument_type=EQUITY`，并按主题 Region、Delay、Universe 和日期过滤。
4. 读取每个 Alpha 的完整详情。
5. 先做身份和主题边界筛选：已提交/隐藏/重复表达式、Region、Delay、Universe、Neutralization、禁用 Dataset。
6. 再做通用标准筛选：Sharpe、Turnover、operator 数量、字段数量。

前筛选分类：

- `EXCLUDED`：基础身份或主题范围不符合；
- `FAIL`：已进入检查流程后明确违反硬门槛；
- `PENDING`：字段、指标或平台响应缺失；
- `RULE_CONFLICT`：标准与主题规则冲突。

## 3. PPAC / PPA 检查顺序

对通过前筛选的候选执行只读 `check`：

1. `Failed PPA`：按平台 `is.checks` 统计，`PENDING` 不算失败；`LOW_SHARPE` 的 value 小于 1 时无论显示状态如何都算失败。每一项保存 name、limit、value、result。
2. `MATCHES_THEMES`：主题匹配；`WARNING` 或缺失不能当作通过。
3. `PURE_POWER_POOL_THEME`：是否为纯 Power Pool 主题；明确 FAIL 直接失败。
4. `POWER_POOL_CORRELATION`：Power Pool 相关性；缺失或 PENDING 保留为待定，超过通用标准上限时失败，除非有完整的高相关例外证据。
5. `POWER_POOL_DESCRIPTION_LENGTH` 和 `POWER_POOL_DESCRIPTION_FORMAT`：Description 的技术检查；缺失或待定不能进入 `PPA_PASS`。
6. `SELF_CORRELATION` 作为平台诊断证据保存；通用 PPA 标准中不适用的 `PROD_CORRELATION` 不作为 PPA 硬门槛。

最终分类：

```text
所有硬门槛明确通过 + 所有必需 PPAC 结果明确 PASS -> PPA_PASS
任一明确失败 -> FAIL
无明确失败但存在缺失/PENDING/WARNING/超时 -> PENDING
规则来源互相矛盾 -> RULE_CONFLICT
```

`PPA_PASS` 不等于 `READY_TO_SUBMIT`，也不代表奖项 Description、月度额度或人工提交已经完成。

## 4. 后筛选与报告

每个 Alpha 写入一个分类目录，并保留：Alpha ID、分类、失败原因、数值门槛、Failed PPA 明细、
PPAC 状态和平台检查证据。汇总文件保存各分类数量。

真实平台运行示例：

```powershell
python 代码/ppa_screening_v2/ppa_screen.py
python 代码/ppa_screening_v2/ppa_screen.py --start-date 2026-07-01 --end-date 2026-07-31
```

当前主题的逐项 JSON Pointer 核对表见 README；每个运行报告的 `base_scope` 字段会保存
同一份主题范围快照，避免报告只写“PPA 范围”而无法复核具体值。

## 当前主题的逐项核对

针对 `PPA 范围/20260727_0809_GLB_Power_Pool_Aug26_Rules.json`，基础范围不是一个抽象标签，
而是以下全部条件的交集：

1. `/duration`：2026-07-27 至 2026-08-09，首尾包含；运行日不在该区间时不能产生 `PPA_PASS`。
2. `/core_requirements/region`：必须为 `GLB`。
3. `/core_requirements/delay`：必须为 `1`。
4. `/core_requirements/universe`：必须为 `TOPDIV3000`；`TOP3000` 不视为近似合法值。
5. `/core_requirements/neutralization`：只允许 `Slow Factors`、`Fast Factors`、`Slow + Fast Factors`、
   `Crowding Factors`、`RAM`，且必须在 Settings 显式选择；`NONE` 加表达式内 `group_neutralize` 不等价。
6. `/core_requirements/forbidden_datasets`：`PV1`、`MODEL110` 不允许；`/warnings/dataset_warning` 说明
   support fields 不属于禁用 Dataset 的实质字段，需要字段来源证据才能例外。
7. `/warnings/universe_warning`、`/warnings/neutralization_warning`、`/warnings/dataset_warning`：
   是对上述硬条件的解释和误用警告，必须一起写入报告，不是可忽略备注。
8. `/multiplier` 为 `1X`，只表示主题奖励倍率，不改变技术筛选门槛。

平台候选身份 `EQUITY / REGULAR / UNSUBMITTED` 是进入本主题筛选器的固定查询条件；
它们不是主题文件中可被候选覆盖的设置。
